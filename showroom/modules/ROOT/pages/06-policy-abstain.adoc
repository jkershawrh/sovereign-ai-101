== Objective

Explain why unavailable policy cannot authorize a request.

== Learner actions

. Inspect the `fault` record on case `policy-unavailable`: the illustrated fault is `opa_unavailable`, scoped only to `rehearsal-session-101`, with a healthy ledger.
. Follow the simulated activate → submit → restore sequence. This package has no live fault switch and sends no requests.
. Inspect the general prompt under a new request ID `rehearsal-policy-unavailable`: HTTP 503, classification `general`, decision `abstain`, reason `policy_unavailable`, execution `not_started`.
. Verify absence of generated text/model fields, zero simulated OVMS calls, and the fresh `router.request.abstained` receipt.
. Record the restore time and name the platform operator as recovery owner.

*Blocked live procedure:* a qualified harness must make the actual boundary encounter an unavailable OPA response for this session. The learner activates and restores it; never stop shared OPA or manufacture an API result.
Missing, null, nonboolean, malformed, timeout and non-2xx policy results all require abstention before dispatch. Current source fails open on several of these paths; this is a new requirement, not an existing feature.

An abstention is not a model refusal or a renamed HTTP error. The healthy ledger permits the abstention receipt in this case.
Ledger-loss engineering tests are separate: failed pre-dispatch acknowledgement must prevent dispatch without inventing a receipt; failed completion acknowledgement after dispatch must withhold text and report execution as failed or unknown honestly.
